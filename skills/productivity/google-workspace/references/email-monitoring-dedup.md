# Stateful Gmail/Calendar monitoring

When using this skill for scheduled inbox/calendar scans, treat duplicate alerts as a bug.

## Recommended pattern

1. Load persistent state before scanning, e.g. `~/.hermes/state/email-check-state.json`.
2. The state file may contain both `notified_ids` and `notified_hashes`; treat either one as sufficient to suppress a candidate.
3. Normalize hash tokens before comparison: treat bare SHA-256 digests and prefixed forms like `sha:` / `sha:event:` as equivalent so legacy state still dedupes cleanly.
4. For Gmail, dedupe on both:
   - the Gmail message id, and
   - a computed stable hash for the notification unit (prefer thread-level hash if you want one alert per thread).
5. For Calendar, dedupe on both:
   - the event id, and
   - a computed stable hash from summary/start/end/location/description (or equivalent stable fields).
6. Remove any candidate already present in either `notified_ids` or `notified_hashes` before producing user-facing output.
7. If no new candidates remain, output exactly `[SILENT]`.
8. If new candidates remain, update the same state file in the same run before returning the report.
9. If auth fails, report the auth failure once concisely instead of replaying prior alerts.

## Practical note

A thread-level hash is useful for mailing lists and multi-message threads because it prevents multiple alerts for the same conversation when Gmail surfaces several messages from the same thread.

Do **not** use only a coarse thread-level hash for transactional senders that can place distinct real-world items in the same Gmail thread. Amazon/payment/order-style failures with the same subject may represent separate orders minutes apart; include a stable transaction key such as order number, reservation/confirmation number, invoice/boleto id, or total+message id in the hash so one failed order does not suppress another.

## Session notes

- In Hermes workers, if you need to parse the on-disk state as strict JSON, read the file directly from disk in the worker/terminal instead of using the line-numbered file reader output. The file reader is excellent for inspection, but its `LINE_NUM|CONTENT` formatting is not raw JSON.
- Gmail search payloads can include raw control characters or very HTML-heavy snippets; if strict JSON parsing fails, switch to a tolerant parser and re-fetch the small final candidate set with `gmail get` before deciding relevance.
- Some calendar finder wrappers validate the ordering enum case-sensitively and require `startTime` rather than `starttime` or `updated`.
- Gmail monitoring is cleaner if you normalize on one canonical alert per thread after relevance filtering. When collapsing a thread, persist **all Gmail message IDs observed in that thread**, not just the representative message ID, so later Gmail searches cannot re-alert a sibling message from the same conversation.
- For combined Gmail + Calendar scans, keep a single post-dedup candidate list and render the final report directly from that exact list after the state file has been updated. Do not hand-rewrite or trim the report from memory, or a newly detected item can be accidentally omitted even though it was persisted.
- Treat the dedup state file as safety-critical: if `~/.hermes/state/email-check-state.json` is missing, initialize it; if it exists but cannot be parsed, fail closed with a concise state/auth-style error instead of alerting from an empty state, because duplicate notifications are worse than a missed cron run.

## False-positive guardrails seen in real runs

- Google Calendar notification emails (for example from `calendar-notification@google.com` / Google Agenda) are usually duplicate reminders/agenda digests for events already covered by the Calendar scan, not standalone Gmail alerts. Do not alert them merely because the subject contains `Notificação`, `convite`, or other generic calendar/action words; only surface the underlying Calendar event if it survives the calendar relevance filter.
  - Some Google Workspace backends may return only the display name (`Google Agenda`) instead of the full `calendar-notification@google.com` sender on broad Gmail searches. Keep subject/snippet/body hard exclusions too: suppress `Google Agenda` messages with subjects like `Notificação: ...`, `Você não tem nenhum evento programado...`, birthday reminders, and invite notifications unless the underlying Calendar event independently survives the calendar relevance filter. If one is accidentally persisted, repair `email-check-state.json` in the same run before final output.
- Treat newsletter/media senders as irrelevant even when they discuss government topics in the subject or body; the sender still needs to be an actual official source. In code, apply hard newsletter/media exclusions before broad keyword matches so sports/news digests are not pulled in by incidental words. This includes mainstream-news/newsletter senders such as G1/Globo: subjects mentioning `governo`, `INSS`, politicians, biometrics, fraud, etc. are news coverage, not government notices, unless the sender itself is an official `.gov.br`/public-agency source or the message contains a concrete personal action item.
- Treat provider newsletters and promotional bank/financial marketing as irrelevant even if they contain generic health/security/finance words (for example Care Plus newsletters or Itaú account ads); require a concrete actionable item such as an appointment, bill, statement, due date, login/security alert, or school notice. Avoid matching bare generic terms like `pedido`/`booking` unless the sender and surrounding text clearly indicate a transactional order/reservation rather than marketing.
- Suppress bank rewards/points/cashback availability emails (for example Itaú “pontos do cartão de crédito disponíveis”) as marketing/benefits updates, not financial alerts. Only alert bank/rewards senders when the message contains a concrete bill, charge, payment failure, due date, statement, security alert, or explicit account action.
- Treat restaurant/retail coupon and discount emails as irrelevant even if they contain purchase/order vocabulary like `pedido`, `app`, `R$`, or a merchant name; only flag merchant emails when they are clearly transactional (order confirmed, out for delivery, delivered, payment failed, receipt/invoice) rather than promotional (`cupom`, `desconto`, `% off`, `ganhe`, `oferta`).
- Treat legal-info/content-marketing emails (for example Jusbrasil newsletters) as irrelevant even if they include safety/security words like `segurança`, `confere`, or `acesso`; only flag security/account alerts when tied to a real account, reservation, login, password/PIN reset, suspicious access, or required action.
- Treat sports/news digests, vehicle/loan discount promos, mileage coupon campaigns, generic travel upsell campaigns, and medical/check-up marketing invitations as irrelevant even when they contain superficially actionable words like `boleto`, `débito`, `débitos`, `cupom`, `viagem`, `prevenção`, or a user name. Require concrete transaction evidence: confirmed booking/order, shipment, payment, appointment created/changed/cancelled, bill due, security alert, or an explicit required action.
- In Portuguese email monitors, avoid bare substring security matches such as `senha`: it can fire inside unrelated words like `resenha` in sports/news digests. Use word boundaries or token-aware matching (for example `\bsenha\b`) and keep sports/newsletter hard exclusions ahead of security keyword checks. If a false positive was already persisted, repair the dedup state in the same run before returning the final output.
- In particular, Gringo/vehicle-fee coupon campaigns such as “Feirão do Veículo em dia” or “Cupom de 50% OFF” are promos, not financial alerts, even when the snippet mentions paying/parceling vehicle debts. Only alert Gringo/vehicle emails when they state a specific existing debt, charge, due date, payment failure, paid receipt, or required account action.
- Do not persist candidates until after final relevance filtering. If false positives are discovered after state has already been updated in the same run, repair the dedup state before final output by removing those candidates' message/event IDs and computed hashes, and correct run counts so the false positives can be handled properly in a future scan.
- Build cron monitors with an explicit dry-run/commit boundary: use dry-run or local candidate inspection while tuning relevance, then perform exactly one committing run whose output is the final report. Do **not** run the committing monitor a second time just to verify output; the second run should correctly return `[SILENT]` after deduplication and can overwrite/confuse the report you need to deliver. Verify by checking state membership or by using a non-mutating dry-run path instead.
- Add a final deterministic sanity filter over the exact alert list immediately before persisting and returning it. This last pass should enforce hard exclusions (sports/news digests, newsletters, promos, Google Calendar notification emails) even if earlier heuristic code marked them relevant. If a false positive is noticed after the state update, repair the state in the same run by removing those IDs/hashes and return the corrected final output (often `[SILENT]`) rather than delivering the stale pre-repair report.
- When writing helper scripts in Python, do not pass shell parameter-expansion syntax like `${HERMES_HOME:-$HOME/.hermes}` to `os.path.expandvars`; Python will not interpret the `:-default` form. Resolve defaults explicitly with `os.environ.get('HERMES_HOME') or str(Path.home()/'.hermes')` before constructing paths to `google_api.py` or `setup.py`.
- In cron monitors, if `setup.py --check` succeeds but `google_api.py` fails through the optional `gws` backend with an OAuth/invalid-credentials message, verify with the bundled Python backend before reporting auth failure. A practical way is to run `google_api.py` with a `PATH` that excludes the Hermes node bin containing `gws` (or otherwise ensure `_gws_binary()` is false), while keeping the same `~/.hermes/google_token.json`. Use the Hermes/agent virtualenv Python that has the Google API dependencies installed (for example the active Hermes venv), not a bare system `python3` that may lack `googleapiclient`. Treat this as a backend fallback, not as permission to replay old alerts.
  - Concrete cron-safe fallback pattern:
    ```bash
    PATH=/usr/local/sbin:/usr/sbin:/usr/bin:/sbin:/bin \
      /root/.hermes/hermes-agent/venv/bin/python \
      /root/.hermes/skills/productivity/google-workspace/scripts/google_api.py \
      gmail search "in:inbox newer_than:1d" --max 100
    ```
    Use the same prefix for `calendar list`. This forces `_gws_binary()` to be false in environments where the `gws` backend is present but using stale/invalid credentials, while still using the Hermes OAuth token through the Python client.
- Calendar scans should not treat every upcoming event as alert-worthy by default; apply the same relevance standard as Gmail unless the monitoring job explicitly asks to report all new calendar events.
- When a calendar or inbox notification is clearly just a reminder/update and not a real actionable item, keep it out of the alert set unless it matches a high-confidence school/financial/security case.
- Do not treat a recipient/name personalization alone (for example “Demetrius, …” marketing subject lines) as relevance. Personalization is common in promos/newsletters; require concrete transaction evidence, a school/financial/security source, or an explicit required action.
- Suppress Google Family Link / family-safety feature marketing emails (for example “Demetrius, é hora de descansar! Prepare-se com o Family Link”) when they only promote screen-time, location, or spending-monitoring features. Only alert family/account emails when they report a concrete child-account safety issue, purchase/charge, policy action, suspicious access, required approval, or setup action the user must take.
- Suppress gym/club/fitness marketing even when it contains account-ish words like “projeto”, “recomeça”, “mensalidade”, “gratuito”, or Gmail `IMPORTANT`; only alert fitness/club emails when they are clearly billing, cancellation, booking, safety, access/action notices, or a high-confidence family-paid benefit invitation (for example “Fernanda fez uma assinatura do Wellhub para você”) that explicitly says a named family member already paid and the user must create/activate the account.
- Treat Amazon Subscribe & Save / `Programe e Poupe` “Revise sua entrega recorrente” messages as transactional recurring-delivery alerts, not mere promotions, when they include concrete delivery timing or a last date to manage the order. In the summary, include the management deadline and expected delivery date when available.
- Suppress school/university lead-generation marketing (for example vestibular/graduação/college ads) even when it contains words like “oportunidade”; only classify as recruiter/job outreach when the sender is an employer/recruiter/platform and the message is about work, hiring, application, contract, or paid project participation.
- For final user-facing alerts, prefer fetching the full message for each post-dedup candidate (`gmail get`) before summarizing when the search snippet is too generic; Agenda Edu snippets often hide the actual actionable body details behind repeated boilerplate.
- For `Eleva`/school matching, require a true school source or token-aware school reference (for example Agenda Edu, `Escola Eleva`, or `\beleva\b` in a school context). Do not use loose substring/body keyword matches that can misclassify unrelated newsletters. If a newsletter false positive was already persisted, repair the state in the same run before returning `[SILENT]` or the corrected report.
- Treat high-confidence school exam/assessment communications from Agenda Edu / Escola Eleva as relevant even when they are not a calendar date change or payment/security alert. If the full body gives parent guidance (sleep, food, screen-time, anxiety support, required reading confirmation), summarize those concrete actions instead of the generic `novo comunicado` snippet, and persist the message/thread ID variants before returning the alert.
- Google Agenda daily agenda emails that say there are no events, birthday/event reminder emails, and Google Calendar invitation notifications should generally be suppressed as Gmail alerts; surface only the underlying Calendar event if it independently passes calendar relevance filtering.
- Suppress routine one-time verification code emails (for example Wellhub “Your verification code”) unless the surrounding text indicates suspicious access, password/PIN reset, or an account-security problem. A verification code email that immediately follows a previously alerted onboarding/activation email is usually just the user's expected follow-through and should not trigger a second alert.
- Suppress routine family-safety/activity digest emails (for example Microsoft Family Safety “Weekly activity report for Caio”) when they only say a report is available or summarize normal activity. Only alert family-safety senders when the message reports a concrete child-account safety issue, purchase/charge, suspicious access, policy/enforcement action, required approval, or setup/action item.
- Suppress loyalty/travel/news/media/club newsletter emails such as Hilton bonus-points campaigns, Booking.com campaign/travel-tips emails, Tennis Channel match/news digests, restaurant “brinde” promos, Jockey Club Brasileiro newsletter/news items (for example staff/emergency training stories), and `the news ☕` newsletters even when their body contains generic financial/security/travel words. Only alert travel/hotel/club senders when the email is a concrete reservation confirmation/change/cancellation, check-in/action deadline, payment failure, receipt/invoice, membership/account action, or actual booking/scheduling update.
- Suppress post-trip airline/hotel survey or review-request emails (for example Azul “Queremos saber sua opinião sobre a viagem...”) even when the subject/body asks the user to respond; these are low-signal feedback requests, not actionable travel/account alerts. If such a false positive was persisted, repair the dedup state in the same run before returning the corrected report.
- For Booking.com specifically, distinguish transactional property/reservation messages from campaign mail: `noreply@booking.com` property messages that include a confirmation number, arrival timing, or host/property instructions are alert-worthy; `email.campaign@sg.booking.com` / campaign-style destination tips such as “informações úteis para sua viagem” are promotional/travel-content emails and should be suppressed unless they include a concrete required booking action, payment problem, check-in deadline, or reservation change/cancellation.
  - Implementation pitfall: put this campaign-sender exclusion ahead of generic “transaction/action” keyword matching. Do not let words like `booking`, `viagem`, `reserva`, `Rio de Janeiro`, or HTML-heavy travel-tip body text promote Booking campaign mail into an alert. If such a false positive was already persisted in the same run, remove its Gmail id/hash from `email-check-state.json`, correct run counts, and return the repaired final output (often exactly `[SILENT]`).
- Airline marketing/news senders such as Azul `noreply@voeazul-news.com.br` should be suppressed for hotel upsells, fare alerts, points/bonus campaigns, and post-trip surveys, even when the copy says the user already has a flight, picked a date, or asks them to respond. Only alert airline mail when it is a concrete booking/itinerary change/cancellation, check-in/action deadline, payment failure, receipt/invoice, or safety/account notice.
  - Implementation pitfall: if you fetch the full message with `gmail get`, do **not** let the returned payload overwrite richer search metadata such as the original `from` address, labels, or thread context before final hard exclusions. Some backends normalize `from` to a display name like `Azul`, which can bypass domain-based exclusions unless the original search sender is preserved separately.
- Do not blanket-exclude all senders with `marketing` in the address. Some systems use marketing-looking senders for transactional items: Rio Tennis Academy `marketingriotennis@gmail.com` can send real tennis scheduling updates such as “Jogo do Ranking - Convite Aceito” with match date/time/court, and these should alert when they include concrete booking/confirmation details. Still suppress generic tennis/gym/club promos.
  - Rio Tennis Academy ranking messages that say a scheduled match was **cancelled**, accepted, or changed are actionable scheduling alerts. If a later cancellation arrives for the same match, suppress/persist the earlier reminder too so a future run does not re-alert the stale reminder after the cancellation.
- Camp/school-trip operational messages from systems like CampSite (`services@mail.campsite-mail.com`) are alert-worthy when they include concrete pre-arrival details for the user's child (arrival window, campus address, flight-information form, parents dashboard, handbook/packing list). Treat these as school/travel logistics, not newsletters.
- Prime Video / digital-content “order confirmation” messages can be relevant purchase alerts when they include an order number; keep the summary terse and include the order id. Do not promote Prime Video marketing/recommendation emails without an actual order/receipt.
- Hostinger or cloud-provider payment-failure notices for named services/servers (for example KVM/VPS hostnames) are relevant finance/infra alerts; include the affected service/hostname and the fact that payment did not complete.
- Lowndes condominium boleto emails from `naoresponda@lowndes.com.br` with subjects like “Boleto digital - ... - Vencimento: DD/MM/YYYY” are financial alerts even when `gmail get` returns an empty body; use the search snippet/subject as sufficient evidence and include the due date.
- Reverde open-account/payment-reminder emails from `contato@reverde.com.br` are financial alerts when they identify an installation, month, boleto/linha digitável, or amount. Include the installation/month and amount when present; if the body says “caso já tenha realizado o pagamento, desconsidere,” still surface it as a bill/payment status alert rather than suppressing it as marketing.
- Itaú Shop / Sempre de Samsung transactional emails from `sempredesamsung@itaushop.com.br` are purchase alerts when they say a real order was received/approved or include a concrete product and delivery estimate. If a “pedido recebido” message is immediately superseded by a “pedido aprovado” message for the same purchase in the same scan, persist both message IDs/hashes for dedup safety but only alert the later approval so the user does not get two alerts for one order.
- Official bank/account contract-change notices can be relevant account-document alerts even when they explicitly say “nothing to do now” (for example Nubank “Atualização do Contrato de Conta”). If surfaced, summarize the substantive change and state clearly that the email says no action is required; do not inflate it into an urgent/action-needed alert.
- Calendar auto-created travel/hotel events may be duplicates of previously alerted Gmail bookings or already persisted calendar IDs. Always apply calendar ID/hash dedup before surfacing; do not re-alert a Gmail-derived calendar event such as “Stay at ...” if the calendar event ID is already in `notified_ids`.
- Before committing state for newly relevant emails whose search snippet is generic (for example CampSite/San Patricio, DocFiscAll/NFSe, or HTML-heavy retailer mail), fetch `gmail get` and render the final alert from the full body details, not from placeholder labels like “operational/financial notice.” Persist only after this full-detail summary pass, or repair the state in the same run if a generic summary was accidentally committed.
